# ADR 0002. 계산 엔진은 이벤트 재생(replay) 방식

- 상태: 채택 (2026-10-31)

## 맥락
소급 입금(G11), 입금 취소(G27), 정정 이동(G28), 금리·약정일 변경(G24·G25), 기한이익상실 소급 취소(R5)는 모두
"과거 어느 날부터 다시 계산"을 요구한다. 상태를 갱신하는 방식(증분 계산)으로는 경우마다 되돌리기 로직이 따로 생긴다.

## 결정
- `servicing.engine.LoanSimulator`는 계약 조건(`LoanTerms`, 금리 이력 포함)과 이벤트 목록(입금·중도상환 요청·약정일 변경·비용)을 받아
  실행일부터 기준일까지 **하루씩 재생**하는 순수 함수다. DB·Spring·시계에 의존하지 않는다.
- 하루 처리 순서: 유예 기한이 지난 회차 연체 판정 → 통지 취소·상실 → 상실 사유 판정 → 금리 변경 재산출 → 비용 → 입금 → 약정일 가수금 충당 → 중도상환 → 약정일 변경.
  R24의 일마감 순서(①~④)와 같은 방향이다.
- 기산일(R13)은 엔진이 은행 거래일자와 그 시점 스케줄로 정한다.
- 이자는 정산 이벤트에서만 확정(R1)하고, 구간은 하루 단위 기준(기준금액·이율)이 바뀌는 곳에서 나눈 뒤 구간별 절사(R2·R12)한다.
- 엔진 출력(`Posting`)은 원장 거래의 "있어야 할 모습"이다. 저장 계층은 저장된 유효 거래와 키(유형·원 이벤트·기산일)·금액을 비교해
  달라진 거래만 REVERSAL + 새 거래로 남긴다(R26). 원장 행은 수정·삭제하지 않는다.
- 기한이익상실 통지는 저장된 사실(`KnownNotice`)로 엔진에 다시 넣는다. 재생 결과 사유가 없어진 통지는 VOID → 저장 시 REVOKED/CANCELLED(R5).
  처리일보다 과거에 생겼어야 할 새 사유는 `detectFrom`(처리일)로 미뤄 기록한다(R29).

## 결과
- 같은 입력 → 같은 결과(결정성)를 테스트로 보장한다.
- 계약 1건 재생은 최대 수천 일 루프라 MVP 규모에서는 충분히 빠르다. 대량 일마감에서 느려지면 "마지막 마감 스냅샷부터 재생"으로 최적화할 수 있다(확장 지점).
