# ADR 0012: 일마감 계약 단위 실패 격리

- 상태: 채택
- 날짜: 2026-11-15
- 규칙: 정책서 R76 (R24 처리 순서의 ③·④ 판정 단위)

## 배경

일마감(`DailyClosingService.close()`)의 ②~④는 `LoanAccountService.judgeAll()`이 열린 계약마다 REQUIRES_NEW 트랜잭션으로
재생한다. 그런데 반복문이 예외를 잡지 않아, 계약 하나의 재생이 실패하면 남은 계약의 판정, ⑤ 대사, 일보 스냅샷, 업무일자 변경이
모두 멈췄다. 실무에서 매입(양수) 데이터 한 건이 잘못 입력되어 전체 마감 일배치가 돌지 않은 장애가 있었다. 한 건의 데이터 오류가
수천 건의 연체·상실 판정과 다음 날 업무 전체를 막아서는 안 된다.

## 대안

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| A. 전체 중단 (기존) | 모든 계약이 항상 같은 날짜 기준. 운영자가 반드시 원인을 본다 | 한 건 때문에 전 계약 판정·문자·일보·업무일자가 멈춘다. 다음 날 업무 시작 전까지 못 고치면 장애가 커진다 |
| B. 격리 후 진행 | 실패한 계약만 그날 판정이 늦고 나머지는 정상. 업무일자가 넘어가 다음 날 업무가 열린다 | 실패를 놓치면 그 계약만 계속 판정되지 않는다(실패 기록·일보 표시·ERROR 로그로 보완) |
| C. 실패 임계치 초과 시 중단 | 대량 장애(스키마·코드 버그)는 멈추고, 소수 데이터 오류는 넘어간다 | 임계치(건수·비율)를 근거 있게 정하기 어렵다. 임계치 바로 아래의 대량 실패는 그대로 넘어간다. 중단 시에는 A와 같은 문제 |

## 결정

**B. 격리 후 진행.**

- 반복은 `JudgeRun.run()`으로 분리해 계약마다 예외를 잡는다. 실패한 계약은 그 계약의 트랜잭션만 롤백되고 실패 목록(`JudgeReport.failures`)에 남는다.
  - `BusinessException`이면 BUSINESS + 오류 코드, 그 밖의 `RuntimeException`이면 SYSTEM + 예외 클래스 이름. 메시지는 첫 줄 200자 요약.
  - 실패한 계약은 `asOf`가 마감 전 그대로 남는다. 재생은 결정적이므로(ADR 0002) 데이터를 고친 뒤 다음 마감(`findIdsToJudge`가 `asOf ≤ 판정일`인 계약을 다시 고름)이나 재판정 때 같은 입력으로 따라잡고, 처음부터 실패하지 않았던 것과 같은 결과가 된다.
- 마감은 실패가 있어도 ⑤ 대사 → 일보 스냅샷 → 업무일자 변경까지 진행한다. `daily_closing.judge_failures`에 실패 건수, `report_daily.unjudged_count`에 미판정 계약 수를 남기고 ERROR 로그를 남긴다.
- 실패 기록 `daily_closing_failure`(operation 모듈)는 추가만 하고, 수정은 해결 표시(`resolved_at`·`resolved_by`를 한 번 채우기)만 DB 트리거로 허용한다. 같은 날 마감을 다시 실행해도 같은 계약의 미해결 기록을 또 만들지 않는다.
- 재판정 `POST /api/operation/accounts/{id}/rejudge` (admin.manage = 9.1 "직원·권한·코드·배치 관리")
  - operation → servicing은 공개 API `LoanAccounts.rejudge()`로만 부른다(Repository 직접 참조 없음, ArchitectureTest).
  - servicing은 계약 락(`lock()`, `FOR UPDATE`) 안에서 업무일자까지 재생한다. 일마감 D는 다른 계약을 D+1(= 마감 후 업무일자)로 판정하므로 같은 기준이 된다.
  - operation은 같은 트랜잭션에서 락을 잡은 뒤 해결 표시를 하므로, 같은 계약의 동시 재판정은 뒤의 요청이 기다렸다가 ALREADY_RESOLVED(422)가 된다(앞의 요청이 끝난 뒤 들어오면 FAILURE_NOT_FOUND 404).
  - 재생이 다시 실패하면 아무것도 바꾸지 않고 REJUDGE_FAILED(422)를 돌려준다.
- 재생 입력 무결성: 엔진은 실행(양수)일부터 하루씩 진행하므로 그보다 이른 이벤트는 조용히 빠진다. 입력 단계 검증(`PAYMENT_DATE_INVALID` 등)을 거치지 않은 데이터(이관·직접 수정)를 버리지 않고 오류로 드러내도록 `AccountReplayer.replay()`에서 검사한다. 이것이 "잘못 입력된 양수 데이터"가 일마감에서 실패로 잡히는 경로다(`DailyClosingIT`).

## 남은 위험

- **미판정 계약의 연체 통지가 하루 이상 늦어질 수 있다.** 실패한 계약은 그날 ③ 연체·④ 상실 판정을 받지 못하므로, 판정에 따라 만들어지는 기한이익상실 통지 사유와 다음 날 자동 문자(연체 1·7·30일째 등)가 재판정 때까지 생기지 않는다. 그날 추심 일 배치(소멸시효·약속 판정)도 그 계약의 마감 전 상태로 돈다. 늦게 재판정하면 사유 발생일은 R29처럼 처리일로 기록된다.
- 실패를 계속 방치하면 그 계약만 매일 실패한다. 일마감 이력의 '판정 실패' 열, 일보의 "미판정 계약 N건", ERROR 로그로 드러낸다(알림 연계는 하지 않음).
- 코드 버그처럼 모든 계약이 실패하는 상황에서도 업무일자가 넘어간다(대안 C를 택하지 않은 대가). 이때는 판정 실패 건수가 전체 계약 수와 같게 보이며, 수정 배포 후 다음 마감에서 모두 따라잡는다.
