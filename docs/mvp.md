# MVP 범위와 CLAUDE.md

범위는 “좁고 깊게”입니다. 계약 하나의 돈 흐름(이자·입금·취소·연체)을 실무 예외까지 정확하게 만들고, 나머지 업무는 뼈대 하나만 두거나 README의 확장 지점으로만 남깁니다. 실제 업무 전체를 옮기는 것은 목표가 아닙니다.

## 1. 범위

| 구분 | 기능 | 완료 기준 |
| --- | --- | --- |
| **깊게** ① 계산·원장 | 값 객체, 상품 P1\~P5·N1(시드), 계약 생성·양수 등록 API, 스케줄 4종 + 자유상환, 일할 이자 엔진, 금리·약정일 이력과 재산출, 원장·충당 내역, 중도상환·완제 | G1\~G6, G9, G10, G12, G15, G17, G18, G20, G22, G24, G25 |
| **깊게** ② 입금 | 입금 충당, 가수금, 미확인 입금 매칭, 소급 재계산, **입금 취소·정정** | G7, G11, G26\~G28 |
| **깊게** ③ 연체·배치 | 연체 판정, 기한이익상실 통지·상실, 일마감 순서(R24), 업무일자 | G8, G16, G21 |
| **깊게** ④ 보안 | 로그인·잠금, 역할별 권한(정책서 9.1), 접근 기록, 고객 식별번호 암호화 + 블라인드 인덱스 | 권한표대로 허용·차단 통합 테스트 |
| **깊게** ⑤ 화면 | 계약 목록, 계약 상세(요약 바 + 스케줄·원장·이력 탭), 입금 등록·취소·정정, 미확인 입금 매칭 | 화면에서 G11·G27·G28 재현 |
| **한 줄기** | 신청 상태 머신 → 실행 → 계약 이관(Outbox) 1개 흐름 | 신청부터 계약 생성까지 통합 테스트 1건 |
| **한 줄기** | 대외 연계 1종: 가상계좌 입금 통지 웹훅(Mock) → 자동 충당 | 중복 통지·재시도 테스트 |
| **한 줄기** | 엑셀 일괄 처리 1종: 입금 일괄 등록 (업로드 → 검증 → 실행 → 실패 행 다운로드) | 1,000행 파일 처리 |
| 여유 있으면 | 추심 연락 7일 7회, 소멸시효 계산, 분할납부 약속, 채무조정 (기대값은 이미 있음) | G13, G14, G19, G23 |
| 만들지 않음 | 아래 “5. 범위 밖 기능” | README에 확장 지점으로만 기록 |

구현 순서는 ① → ② → ③ → 저장소(DB) → ④ → ⑤ → 한 줄기 3종 순입니다. 이자 엔진은 스케줄에 의존하지 않는 구조(잔액 변경일 기준 구간 분할)로 먼저 만들고, 분할상환 스케줄은 그 위에 얻습니다. 계약은 심사 없이 API로 바로 만들 수 있게 하고, 신청 흐름은 나중에 같은 API를 호출하도록 붙입니다.

## 2. 저장소 구조

```text
loan-servicing/
├─ CLAUDE.md
├─ docs/
│  ├─ guide.md            # 이 문서 '구현 가이드' 탭을 내보낸 것
│  ├─ policy.md           # '가상 회사 정책서' 탭
│  ├─ golden-cases.md     # '계산 검증 사례' 탭
│  ├─ mvp.md              # 'MVP 범위·CLAUDE.md' 탭 (범위표·범위 밖 목록)
│  └─ adr/                # 설계 결정 기록 (0001-day-count.md …)
├─ src/main/java/com/example/loan/
│  ├─ common/       # Money, InterestRate, DateRange, BusinessCalendar, crypto, audit
│  ├─ product/
│  ├─ servicing/    # LoanAccount, schedule, interest, ledger
│  ├─ payment/      # Payment, UnmatchedDeposit, allocation
│  ├─ collection/   # delinquency, acceleration
│  ├─ customer/
│  └─ staff/        # security
├─ src/main/resources/db/migration/   # Flyway
├─ src/test/resources/golden/         # G1~G28 CSV
└─ docker-compose.yml                 # postgres, redis
```

## 3. CLAUDE.md 초안

저장소 루트에 그대로 넣고, 결정이 바뀌면 여기부터 고칩니다.

```markdown
# CLAUDE.md

## 프로젝트
가상의 대부업체 '예시대부'의 여신관리 시스템(포트폴리오). Java 21, Spring Boot 3, PostgreSQL, Gradle.

## 기준 문서 (충돌 시 이 순서로 우선)
1. docs/policy.md — 모든 업무 규칙과 숫자. 9~10장(R1~R33)이 본문보다 우선
2. docs/golden-cases.md — 계산 기대값. 테스트가 이 값과 다르면 코드를 고칠 것 (기대값 수정 금지)
3. docs/guide.md — 설계 방향과 일반론. 수치·규칙이 policy.md와 다르면 policy.md를 따를 것. 16.2~16.3의 엔티티 필드·상태 코드는 스키마 기준

## 범위
- 구현 범위는 docs/mvp.md 1장 표가 전부. 5장 ‘범위 밖 기능’은 구현하지 말고, 필요해 보이면 README 확장 지점에 적기만 할 것

## 판단 기준 (언제 멈추고 언제 진행하는가)
- 업무 규칙(금액·날짜·상태가 바뀌는 규칙)이 policy.md에 없거나 두 가지로 읽히면: 구현을 멈추고 질문. 답을 받으면 policy.md 9장에 R번호로 추가한 뒤 진행
- 기술 결정(테이블·컨럼 이름, API 형식, 화면 배치, 라이브러리): 스스로 정하고 docs/adr/에 기록, 작업 보고에 포함
- golden 기대값과 다르면: 코드를 의심. 기대값이 틀렸다고 판단되면 계산 근거를 보여주고 사용자 승인 후에만 수정

## 절대 규칙
- 금액은 BigDecimal 또는 long(원). double/float 금지. 반올림은 Money 클래스에서만
- 날짜는 LocalDate, 기간은 반개구간 [from, to). 시간대 Asia/Seoul
- 기준일은 업무일자(BusinessDate)와 주입된 Clock에서만. LocalDate.now() 직접 호출 금지
- 이자는 정산 이벤트에서만 원장에 확정 (policy.md 9장 R1). 일일 배치의 미수이자는 조회용
- 원장(LedgerEntry)은 UPDATE/DELETE 금지. 정정은 역분개 거래로
- 금리·약정일은 이력 엔티티(RateTerm, DueDayTerm)에서 조회. 계약에 현재값 컬럼을 두지 말 것
- 다른 모듈의 Repository를 직접 참조하지 말 것 (ArchUnit으로 검사)
- 고객 식별번호는 EncryptedStringConverter + 블라인드 인덱스. 로그·toString에 평문 출력 금지
- 실제 회사·기관의 이름, 전문 형식, 코드 체계를 넣지 말 것. 외부 연계는 포트 + Mock 어댑터만

## 작업 방식
- 계산 로직은 테스트 먼저: golden CSV를 읽는 @ParameterizedTest를 작성하고 통과시킬 것
- 한 번에 한 모듈. 작업 후 ./gradlew test 전체 통과 확인
- 스키마 변경은 Flyway 마이그레이션으로만 (ddl-auto=validate)

## 명령
- 테스트: ./gradlew test
- 실행: docker compose up -d && ./gradlew bootRun
```

## 4. Claude Code로 진행하는 방법

1. 이 문서의 각 탭을 Markdown으로 내보내 `docs/`에 넣고, 위 CLAUDE.md를 커밋한 뒤 시작
2. 첫 세션: “golden-cases.md의 G1\~G6을 CSV로 만들고, 값 객체와 스케줄 생성기를 테스트 우선으로 구현해줘”처럼 작은 단위로 요청
3. 큰 작업(소급 재계산, 기한이익상실 배치)은 플랜 모드로 설계를 먼저 받고 승인 후 구현
4. 단계가 끝날 때마다 README에 “무엇을 왜 이렇게 만들었는지”를 짧게 남기기 (면접에서 그대로 설명 자료가 됨)
5. 계산 결과가 golden과 다르면 먼저 어느 정책 문장을 다르게 해석했는지 찾게 하고, 정책이 모호하면 사용자에게 확인받아 policy.md를 고친 뒤 진행 (CLAUDE.md ‘판단 기준’과 동일)

## 5. 범위 밖 기능 (README 확장 지점)

구현하지 않지만, 실무에 존재한다는 것과 현재 설계에서 어디에 붙일지를 README에 한 줄씩 적습니다.

| 기능 | 확장 지점 |
| --- | --- |
| 한 고객의 여러 계약 일괄 입금 배분, 보증인·제3자 대위변제 | payment 모듈의 배분 전략 인터페이스 |
| 사망(상속), 개인회생·파산, 신용회복위원회 채무조정 | collection 모듈의 추심 중지 플래그 + 금리 이력 변경 |
| 법조치 상세(지급명령·압류·경매), 경매 배당금·공탁금 입금 | LegalAction 엔티티 + 비용(COST) 충당 |
| 상각 확정, 매각·환매, 매각 후 입금 이전 | LoanAccount 상태 전이 + 원장 CHARGE\_OFF·SALE 거래 |
| 신용정보 보고(정보집중), 신용조회, 본인인증, 펌뱅킹 송금 | integration 모듈의 포트 추가 |
| 문자·팩스·우편, 연락 타임라인 패널 | communication 모듈 |
| 담보·보증인 관리, 담보 시세 연계 | servicing 모듈의 하위 엔티티 |
| 보고서(일보 상세, 연체 전이율, 대손충당금), 회계 분개 | reporting 모듈 + JournalMapper |
| 심사 상세(서류 징구, 자동 거절 규칙, 중개수수료 정산), 플랫폼 접수 | origination 모듈 |
| 수기 조정 거래, 상계, 완제·매각 후 취소(상태 되돌리기) | 원장 ADJUSTMENT 거래 + 결재 |

## 6. 문서 동결 규칙

1. 정책서와 계산 검증 사례는 R33·G28에서 동결합니다.
2. 문서는 구현 중 문서끼리 모순되거나 두 가지로 읽히는 문장이 발견될 때만 고칩니다.
3. 새 기능 아이디어는 5장 표에 추가하고 구현하지 않습니다.
4. 범위에 넣으려면 “기존 기능과 다른 기술 포인트를 하나 이상 보여주는가”를 통과해야 합니다.
